# 从一条手柄消息学会遥操与推理

[离线分步阅读器](pipeline-model.html) · [完整数学模型](research/2026-10-22-pipeline-mathematical-model.md) · [上一份交互实验](signal-timing-report.html)

这份课程不要求先读懂所有公式。每一课只回答一个工程问题：**这个数代表什么、是什么时间的数、接下来谁使用它？** 八课可以分开学习；先尝试练习，再展开答案。例子是教学假设，不是对机器人发送的指令。

## 第一课：目标不等于结果

**本课目标：** 分清 hand、target、command、feedback 四个词。

你将手柄向上移动 3 cm。这是人的运动。映射器说“希望末端向上 3 cm”；IK 说“某些关节应该到这些角度”；网关接受并发布它；电机开始运动，编码器报告到了哪里。这四步可能数值不同，也发生在不同时间。

用单关节教学模型代替六关节：当前位置 0.40 rad，局部末端竖直位移约为每 rad 移动 0.05 m。

$$
\Delta q_{ideal}=\frac{0.03\ \mathrm m}{0.05\ \mathrm{m/rad}}=0.60\ \mathrm{rad}.
$$

理想目标因此为 1.00 rad。假设平滑使本次只走目标差的25%，则 IK 解为0.55 rad。假设随后反馈为0.48 rad：**命令是0.55，状态是0.48**。求解目标只前进7.5 mm，实际暂时前进4 mm；剩余误差既有IK折中，也有执行偏差。不要把这些教学数字当实际Piper参数。

夹爪更直观：命令0 mm，但抓着桃子时反馈32 mm，这并不意味着命令失效。它可能意味着被物体阻挡了。若训练动作标签写成32 mm，就丢掉了“继续闭合”的意图。

**练习：** 如果 `receipt=published_not_acknowledged`，能说机器人已经到0.55 rad吗？训练时应把哪个量放state，哪个量放action？

<details><summary>展开答案与设计含义</summary>

不能。receipt只证明发布调用返回，不证明硬件接收或到位。对当前位置目标接口，state用实际反馈0.48 rad，action优先用有发布证据的0.55 rad。原始手柄与IK结果另外记录。未来若学习“到达轨迹”可以改变标签语义，但必须连同执行器和时间定义一起改变。

**设计规则：** 数据结构分别保存意图、求解结果、最终发布和反馈，不能只存一个叫 `position` 的字段。

</details>

## 第二课：先画时间线，再看频率

**本课目标：** 理解一条消息可能经过多个等待。

假设以下时刻已经处于同一参考时钟，单位ms。这是人为构造的例子：

| 时刻 | 发生什么 | 已经知道什么 |
|---:|---|---|
| 0 | 手柄状态对应时刻 | 希望移动3 cm |
| 5 | 浏览器取得估计位姿 | 不是无限连续真值 |
| 45 | 机器人主机收到包 | 到达时已陈旧45 ms |
| 50 | 控制tick创建intent | 等了下一个tick |
| 67 | poll把请求送给IK进程 | 新增17 ms等待 |
| 70 | IK算完 | 计算本身只3 ms |
| 84 | 控制tick消费结果并发布 | 从手柄时刻算已84 ms |
| 120 | 收到一次反馈 | 反馈自身对应的硬件采样时刻仍要核验 |

现在可以解释“为什么 IK 只算3 ms但还是不跟手”：计算只是70−67，完整输入到发布是84−0。增快求解器到1 ms，若仍要等84 ms那个tick消费，发布时刻可能根本不变。

**练习：** 每秒记录200次，能把这84 ms变成5 ms吗？若任务速度0.1 m/s，84 ms对应多大位置错位量级？

<details><summary>展开答案与设计含义</summary>

记录率不能改变已发生的控制延迟。按恒定速度近似，错位为 $0.1\times0.084=0.0084$ m，即8.4 mm。这个数字忽略了后续驱动响应，仅用于时间误差量级判断。

**设计规则：** 保留每阶段关联ID与时刻，分别优化网络、等待、计算和执行；不能用一个RTT或一个solver耗时代表全链路。未同步时钟时不能直接相减头显和机器人时间。

</details>

## 第三课：侧握决定坐标原点，IK决定关节折中

**本课目标：** 理解重握和正则化为什么会改变轨迹。

按侧握时，系统记住“此刻手柄在哪里”和“此刻机器人末端在哪里”。此后的位移相对于这两个锚点计算。松开后你可以把手放回舒适位置，再握住重新建立锚点；这正是离合的作用。

IK同时追求到目标、少跳动、偏好某些姿态和不越关节边界。单方向近似为：

$$
q_k=(1-\alpha)q_{k-1}+\alpha d_k.
$$

若目标差是0.60 rad、$\alpha=0.25$，连续几次新解的剩余差依次是0.45、0.3375、0.253125 rad。每次都朝目标前进，但并不是一次精确到达。

同样三次更新，10Hz要约0.3s，30Hz要约0.1s。因此固定正则权重遇到网络稀疏输入时，实际表现会更迟缓。真实多关节IK还会受姿态、限位和奇异性影响，不能一概视作上述滤波器。

**练习：** 当前worker同一token内用上一接受解作seed，是否说明机器人已经走到这个seed？为什么不能把增大平滑权重当作万能去抖办法？

<details><summary>展开答案与设计含义</summary>

不说明。seed是求解器的历史解，物理反馈可能落后。增大平滑权重可能降低关节目标跳变，也会增加到达目标的滞后和残差。

**设计规则：** 同时看IK几何误差、新解率、结果年龄和实际跟踪误差。若需要固定毫秒尺度的平滑，应把时域行为显式定义并测量，而不是只保存一个无时间解释的权重。

</details>

## 第四课：高质量记录不应把所有流压成同一个Hz

**本课目标：** 区分采集、写入和训练采样。

原始层可以同时保存不规则的手柄消息、约60Hz的发布命令、更高频反馈与三路30FPS图像。写入线程把这些事件搬到磁盘；它不应该把自己的写入时刻改成事件发生时刻。

如果为了统一格式，每33.3ms只保存“这一刻最新的一份所有数据”，你会失去中间命令、按键变化和原始图像间隔证据。更好的办法是先保留原始多速率数据，再建立可重做的30Hz训练视图。

一个容量例子：三路RGB 640×480×3×30约82.944MB/s。即使最终写成很小的MP4，编码前入队仍可能是原始图像。磁盘线程隔离避免同步阻塞，却不能制造无限带宽或无限内存。

**练习：** 相机平均29.9FPS，但中间缺了200ms，能否视作一条完整30Hz轨迹？插值图像索引是否恢复了缺失内容？

<details><summary>展开答案与设计含义</summary>

不能。平均率可能掩盖局部空洞。复制前一帧或插入索引不产生真实缺失图像；如果这样生成训练视图，必须记录帧年龄、重复标记和有效mask。

**设计规则：** 同时报告平均率、p95/p99/max间隔、dropped、队列峰值、时钟来源；大空洞单独切段/标无效，不能只改文件头的FPS。

</details>

## 第五课：训练样本是一个时间关系，不是一行拼表

**本课目标：** 理解观测在过去，动作标签可以在未来。

设训练网格时刻是10.000s：最近收到的图像为9.980s，反馈为9.995s。按当前因果latest规则，可以把它们放入观测，但应保留20ms和5ms的年龄。若图像阈值是15ms，这份图像就无效；不要因为文件里有它就默认为可用。

若配置action offset一步、频率30Hz，标签选择时刻是10.033333s。假设10.020s发布夹爪闭合目标0m，而实际开度仍为0.032m，则该训练行可以是：

```text
observation.gripper = 0.032 m
action.gripper     = 0.000 m
observation_time   = 10.000 s
action_time        = 10.033333 s
```

这不是矛盾，模型要学的正是“在当前状态下，接下来发什么目标”。未来动作作为标签不属于信息泄漏；把10.020s之后才看到的图像偷偷放入10.000s观测才有问题。

Flow Matching会在生成时间 $\sigma$ 上逐步把噪声变成动作数组；执行时再按物理 $\Delta$ 逐步播放。DiT可以是预测向量场的网络，但不会自动修正这行数据的时间关系。

**练习：** N=16、动作30Hz时首末点跨多久？改成10Hz、N不变，会变成多久？多做几步去噪会改变这段物理时长吗？

<details><summary>展开答案与设计含义</summary>

首末点跨度是 $(16-1)/30=0.5$ s，改为10Hz是1.5s。若最后点保持一个周期，总覆盖分别是16/30s和1.6s；两种定义要明确。去噪步数影响生成计算与质量，不能直接改写动作dt。

**设计规则：** 把dt、动作顺序/单位、归一化、观测选择、action offset、缺失mask和任务标签作为训练产物的一部分保存。不能只保存权重文件。

</details>

## 第六课：动作够多，还可能来不及用

**本课目标：** 学会同时算队列覆盖和首动作提前量。

设 N=16、30Hz，执行K=8步时请求下一段，旧计划还可覆盖8/30=266.7ms。若模型与传输共180ms，预留40ms调度余量，则余量为46.7ms。这说明旧队列不会在该确定时延例子中先耗尽。

但当前代码还有一个独立检查：新chunk第一动作必须在未来。若新chunk首动作安排在请求后80ms，直到180ms才被消费，已经晚了100ms。即使旧队列还有动作，这个新chunk也会被拒绝。

因此至少要同时满足：结果未超deadline、首动作未过期、旧队列有足够覆盖、生成依据的观测未过旧。更长chunk解决不了所有问题；更大lead也可能增加计划陈旧程度。

**练习：** 旧队列500ms，lead80ms，结果100ms后消费，deadline300ms，是否接受？若lead改成140ms，就一定能真机成功吗？

<details><summary>展开答案与设计含义</summary>

第一种仍因首动作在过去而拒绝。改成140ms只排除了这一项问题，仍要检查身份/语义、观测年龄、队列接缝、关节可跟踪性和任务结果。

**设计规则：** 在独立服务器上线前，先做有延迟分布的fake/shadow测试，把这些预算写成明确契约；不能只看到HTTP200就宣告推理链路成功。

</details>

## 第七课：顺滑不等于忠实，直接不等于正确

**本课目标：** 理解后处理应该承担什么责任。

模型预测“从物体左边绕过”与“从右边绕过”，两条都可能合理。若简单平均两条轨迹，结果可能朝中间物体走。平滑不是对所有动作都正确的数学操作。

原生执行保留动作语义，但模型输出如果时间过期、关节名错位或本来就跟踪不了，直接送也不会变好。插值可以减少设定值跳变，但可能改速度和时延；TE平均同一时刻的重叠预测；RTC在模型生成过程中利用仍将执行的旧计划前缀。三者的作用位置不同。

**练习：** 当前已有后台推理线程和动作队列，能称为RTC吗？为了平滑把每段动作都拉长2倍，但不通知模型，可能发生什么？

<details><summary>展开答案与设计含义</summary>

不能称为RTC；当前没有模型采样器内的前缀引导。拉长时间会改变动作何时发生、缓存/前缀与实际执行索引、观测到动作的年龄，还可能破坏接触和抓放配合。

**设计规则：** 原始模型输出、后处理计划、最终发布、实际反馈分别记录；任何重定时都要改变计划时间语义并同步到模型调度/cache。

</details>

## 第八课：把“质量好”改写成可以验收的条件

**本课目标：** 用任务需求推导设计，而非先指定一个万能Hz。

假设某个任务希望时间陈旧带来的平移误差不超过5mm，任务典型速度0.1m/s，则允许的年龄量级为0.005/0.1=50ms。这还没有给标定、IK和执行误差留预算。如果现有链路经常超过100ms，增加训练轮数不能消除这个工程瓶颈。

建议每次实验都回答四组问题：

1. **数据是真的吗？** hash/解码/时间源/事件来源能追溯，未知值没有伪填。
2. **数据及时吗？** 各流年龄、间隔、空洞、网络/IK/执行时延分开测量。
3. **动作实现了吗？** 目标/反馈误差、夹爪事件、双臂时差、最终任务效果。
4. **模型能复用吗？** 训练/部署的单位、坐标、dt、归一化、观测选择一致。

**练习：** 采集QC通过、动作曲线平滑、模型loss下降，三者一起能否证明数据适合训练并能真机成功？

<details><summary>展开答案与设计含义</summary>

仍不能。QC可能没检查任务标签/输入空洞；平滑可能来自过度延迟；低loss可能来自重复静止帧或标签泄漏。还需要任务标注、按场景划分的验证、时间契约检查和实际闭环任务评测。

**设计规则：** 下一步先补Timing QC与传输基准，再做原示范/回放精度对照，随后真实观测shadow模型，最后在明确安排的现场实验中验证真实策略。每一步可单独替换模块、单独复现结果。

</details>

## 学完后的一页检查表

| 遥操采集 | 推理执行 |
|---|---|
| 明确frame、锚点、位姿/夹爪映射 | 明确动作空间、单位、dt、模型版本 |
| 测新手柄信息年龄，而非只看发布Hz | 测逐流观测年龄，而非只看快照创建时间 |
| 分开solver耗时和结果消费年龄 | 分开模型计算、传输和队列等待 |
| 保存意图、IK、命令、反馈全部证据 | 保存预测、合并、消费、发布、反馈全部证据 |
| 原始多速率保存，训练视图可重做 | 设备侧权威调度，模型缓存跟随真实消费 |
| QC、任务标签、数据集划分一起审查 | 时序、跟踪与任务成功一起验收 |

可以用这句话自检：**“在这个执行时刻，系统依据哪个过去的观测，为什么选择这个目标，最终实际做到了哪里？”** 如果能从日志回答它，框架就具备了持续改进数据和执行质量的基础。
