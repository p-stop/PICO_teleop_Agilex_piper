# 如何组织AI开发、对话与交接

日期：2026-10-11；状态提示更新2026-10-15。针对本仓库的工作建议；不是要求每次建立大量文档或并行agent。M1已完成本机fake实现，下面的首实现提示词保留为任务描述示例；接续时先读当前状态，不重复启动已完成里程碑。

## 1. 对话按可验收任务划分

建议保留当前对话用于定位、跨模块设计和重要取舍。开始实现时，新开“fake控制、采集与回放首切片”对话，绑定本仓库，从[agent入口](agent-onboarding.md)和[首切片计划](../plans/001-fake-control-loop.md)进入。

继续当前对话实现也可以；长对话不是必须重开的错误状态。官方[Codex提示指南](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)介绍上下文压缩与仓库指令。本项目建议重开是因为任务阶段和验收边界变化，便于审查结果，不是因为旧对话已经失效。

| 情况 | 建议 |
|---|---|
| 同一故障或同一验收任务的连续修复 | 继续原实现对话，保留日志与推理上下文 |
| 从需求讨论进入实现 | 新实现对话，指定计划、结果和约束 |
| 一个切片验收完成，开始下一个独立交付 | 新任务对话，引用已完成版本与新计划 |
| 独立驱动/输入/策略adapter | 接口有基线后，可分别开对话 |
| 跨模块schema、所有权、安全路径调整 | 一个集成任务主导变更，相关模块随后适配 |
| 对话反复引用废弃方案或目标已大幅变化 | 先更新计划/checkpoint，再开新对话接续 |
| 只读代码审查 | 可独立对话，给固定diff/版本和审查问题 |

一条任务应能描述“用户现在可以做什么”和“如何证明完成”。初期不要为contracts、runtime、data分别让agent自由设计，再期望自然接通。

## 2. 初期先串行，边界稳定后再拆分

首切片由一个实现任务贯通contracts → 图预检 → fake输入/执行 → 仲裁/guard → MCAP → replay，并接入受控延迟的stub policy。依次完成可运行里程碑，而不是一口气生成所有目录和抽象类。

之后可按需建立设备/输入、数据/评测、推理/运动、GUI等任务，**一次只打开确实有独立工作可做的任务**。模块名称是导航，交付仍按端到端场景验收。

| 设计模块（M1仅实现所需子集） | 责任 | 共享契约/前置依赖 |
|---|---|---|
| contracts/graph | 消息、能力、图schema和静态校验 | 版本、类型/单位/frame/time语义；由集成任务统一修改 |
| runtime | session、lease/epoch、guard、时钟 | contracts；停止/接管/过期行为 |
| drivers/plugins/mappers | 设备I/O、输入、明确的语义转换 | contracts、runtime入口；厂商依赖仅驱动边界 |
| data/apps | 原始记录、回放、导出、运行报告 | 共享事件与时间/动作标签；不直接调用硬件SDK |
| policies/scheduling/motion | 模型资产、chunk与执行适配 | 观测/动作契约、epoch和guard；算法按需接入 |
| sim | 固定资产、虚拟执行/观测、reset | 同契约，不伪装真实时间/物理性质 |
| ui/api | 同后端的编辑/运行客户端 | 已稳定schema/session；GUI低优先级 |

首版只建立真正需要的模块。新设备适配前先用fake实现验证接口；不要让未验证硬件驱动反过来决定核心的全部抽象。

## 3. 把记忆放进仓库

- `AGENTS.md`：长期约束与入口，保持短小。
- `architecture.md`：设计边界；`project-status.md`：真实完成度与验证范围。
- `plans/<task>.md`：当前任务范围、里程碑、发现、决策、checkpoint和验收证据。
- `docs/adr/`：长期接口/安全/主机等设计取舍；不把每个实现细节都写成ADR。
- 验证报告：固定代码、依赖、环境、运行命令与结果。小日志可进入计划，大实验数据只存引用/hash。

新对话不要假定已经掌握其他对话的细节，即使同属一个项目。把必要结论转成上述文件，其他内容按需读取。官方建议用可接续、持续更新的计划支撑长任务，同时避免堆积无关仓库指令：[计划实践](https://developers.openai.com/cookbook/articles/codex_exec_plans)、[精简指令建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。

## 4. 共享接口与代码隔离

若用户决定并行任务，先固定共同Git基线，再使用各自分支和独立checkout/worktree。多个对话不是文件隔离机制；同一目录里的改动仍可能相互覆盖。当前仓库尚无commit，先建立可追踪基线再组织并行实现。

任务计划注明允许修改范围和共享文件。contracts、根依赖清单、architecture、project-status由一个集成任务维护；其他任务提出具体修改及理由，集成时统一落地，避免多个任务覆盖全局状态。必要的跨模块变更应扩大该集成任务的范围并更新计划，而非僵硬地绕开接口。

集成不止合并文件：适配调用端、更新版本/迁移说明，跑真实消费方测试与端到端链路。独立模块测试全部通过仍可能没有可运行组合。

## 5. 给AI的任务说明

提供五件事通常就够：可观察目标、允许范围、验收条件、环境、约束。实现方法给agent判断空间；对坐标、单位、硬件型号、动作语义和授权则写清楚。

首实现对话可直接使用：

```text
请阅读 AGENTS.md、docs/agent-onboarding.md、docs/project-status.md、
docs/architecture.md 和 plans/001-fake-control-loop.md。
开始实现该计划中的硬件无关首切片，按里程碑完成可运行的控制、
MCAP记录/回放和stub策略接管链路，并运行相关测试。
开发环境为当前Windows；无Linux或硬件证据时如实报告未验证。
不要接入真实SDK或执行机器人命令，不实现GUI、真实模型、RTC或MPC。
根据实际代码更新计划、必要ADR和项目状态，交付复现命令和测试结果。
```

修复问题时提供复现命令、期望/实际行为和相关日志，不只说“无法运行”。评审时给代码版本/diff，要求按故障场景追踪路径，而非仅评价代码风格。

## 6. 如何判断AI的工作质量

要求能运行的行为和实际证据：拒绝无lease/过期/旧epoch命令；接管后迟到策略结果不执行；记录能读取和验证；坏配置明确失败。测试应能发现这些错误，不只是重复实现的内部判断。

同一个AI编写代码并测试有价值，但不保证测试独立性。关键边界适合另做只读审查，用不同故障条件、乱序/延迟输入和消费方验证，必要时手工核对日志。多agent一致意见不是实测证据。

普通实现决策在已有任务范围内推进；坐标/单位/映射无法确定时先完成不依赖它的部分，再请求必要信息。真机命令仍须明确授权，不因计划中列出未来物理验收就自动执行。

## 7. 跨机器验证

沿用[跨机工作流](development-and-validation.md)：Windows开发/fake，Ubuntu分别运行同版本核心验证，后续再sim/只读/物理。记录源码和依赖版本；未提交修改带patch/hash。聊天迁移不等于源码或实验环境迁移。

现场问题把设备身份、环境、配置、命令和原始日志带回任务计划；避免只转述“另一台电脑失败了”。只读SDK初始化也须检查是否会产生写操作。Linux未执行就写not_run，不能根据Windows通过推断。

## 8. 交接最小内容

每个里程碑或换对话/机器前，记录：目标和当前里程碑、代码基线/改动、实际完成、测试命令与结果、限制、下一步、不能丢失的语义决定。中断任务保留未提交工作并写checkpoint；无需为了交接先做无关重构或重复全部测试。

使用[任务模板](../plans/templates/task-template.md)和[验证报告模板](../plans/templates/validation-report-template.md)，按任务大小删减。不要每轮复制整份架构或整段聊天。
